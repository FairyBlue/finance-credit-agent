## 面试开场

### 三十秒版本

> 我参与一个金融决策 Agent 后训练项目，研究长程工具调用的信用分配。项目在单张 H100 上跑通了 Qwen3-4B 全参数 RL，并实现分块优化器和资源管理。我主要负责【实际负责模块】，可以展开讲【一个具体问题】。

开场中的个人分工只选一项自己能深入讲清的内容。

### 九十秒版本

> 这个项目用离线交易环境研究长程 Agent 的信用分配。模型每次看到当时可用的历史、持仓和工具反馈，输出交易或信息工具调用；环境负责次日开盘成交、费用和状态变化，最后计算金融评分。难点是一个最终分数很难直接说明中间哪个决策有价值。
>
> 项目有两方面工作。训练系统方面，基于 Agent-R1 和 verl 接入环境，用 vLLM 采样，在单张 H100 上完成 Qwen3-4B Actor/Critic 全参数更新。为了处理显存和主存限制，实现了分块 AdamW、CPU/磁盘优化器状态交换和阶段资源准入。算法方面，以均匀分配奖励加 GAE 为基线，比较按动作类别聚合的额外信用信号，并检查它实际进入 loss 后的影响。
>
> 工程上，最近完整对照覆盖两个 seed、四种 RL 配置，共 1,336 条训练和评估轨迹。方法上，旧动作族池化还没有建立稳定收益优势。继续诊断发现，同一天的轨迹可能已经有不同持仓，同样是 buy 也可能是不同订单，所以目前转向相同前缀、具体订单和独立随机后续的验证。
>
> 我个人重点做的是【模块】。一个能体现我工作的问题是【现象】，我通过【证据】定位到【原因或待检验假设】，实施了【修改】，最后用【验证】确认结果。

### 一次训练到底怎么跑

沿下面这条链讲，不要只报框架名称。

```text
冻结行情和 episode
    → 环境生成当时可见的观察、工具 schema 和历史反馈
    → 当前策略通过 vLLM 输出工具调用
    → 环境校验参数，执行或拒单，返回新观察
    → 循环到 episode 终点，计算金融评分 Y
    → 构造 M1 逐步奖励，按实验设置加共同拒单罚项
    → critic 估计动作前状态值，计算逐步 GAE 和 critic return
    → M2 在 GAE 后加入额外 S，再统一 whitening
    → critic 更新，actor 按 GSPO loss 更新
    → 沿上游训推切换与权重同步路径进入下一批采样
```

模型生成的是一段工具调用文本；一个环境交互步骤可包含多个 response tokens。环境步骤、交易日和 token 是三个层次：合法推进动作推进交易日；信息调用和拒单也形成交互步骤，但不推进日期。额外 M2 信号在步骤层构造，再作用于该步骤有效响应 token。

## AI Infra 高频追问

### 为什么 4B 模型还需要这么多显存

> 不能用推理权重大小估算 RL 训练。系统里有 actor、critic、reference 和 rollout 引擎。训练还要存梯度、优化器 moments、激活和临时 buffer，生成还需要 KV cache。按 4B 量级粗估，一套 FP32 参数约 16 GB，两份 FP32 Adam moments 又约 32 GB。多个角色如果同时保留这些状态，单卡很容易放不下。

这里的 GB 是十进制数量级估算，不是项目精确逐张量统计。项目的资源路径保持训练参数在 GPU，重点调整 moments 的驻留与更新方式，同时管理 reference、vLLM、microbatch 和梯度检查点。[低显存训练记录](history/INITIALIZATION_AND_4B_LEARNING.md#拒单罚与低显存训练)

### 分块 AdamW 怎么实现

> 没有修改 AdamW 的算法。我保留 optimizer 和参数对象，用同一个参数、梯度的连续 view，按块取对应的一阶二阶状态到 GPU，调用固定 PyTorch 版本的 functional AdamW，再把更新后的 moments 写回 CPU。外部的梯度累积、全局梯度裁剪和学习率调度保持原路径。

**最容易被深入追问的细节：** 每一块都要使用该参数更新前同一个 step 的副本；不能每处理一块就让原 step 加一。整份参数处理完成后原 step 才加一，否则 bias correction 会改变。

代码对应 [chunked_adam.py](../src/agents/chunked_adam.py)。AdamW 的参数更新及 bias correction 可对照 [PyTorch 2.7 文档](https://docs.pytorch.org/docs/2.7/generated/torch.optim.AdamW.html)。

### 你怎么证明分块更新算对了

> 分两层验证。CPU 数值测试在多步梯度累积和全局裁剪下，对照原生 AdamW，检查参数、梯度和 optimizer state，覆盖不同块大小及无梯度参数。实际 GPU pilot 则确认两轮角色更新和 moments 恢复能完整执行。前者检查受测条件下的数值一致性，后者检查真实接线与资源行为。

CPU 测试使用 `rtol=0, atol=0`，不能据此宣称整套 GPU 训练与原生 AdamW 位级等价。[数值测试](../tests/test_chunked_adam.py)；[GPU pilot 完成收据](../runs/m2-low-memory-handoff-20261004/completion_readout.json)

### 64 MiB 是什么意思训练快了多少

> 64 MiB 是分块优化器临时张量的预算，包含相应 moments 和计算中间量。它不包含模型参数、梯度、激活和其他角色占用，也不等于 allocator reserved。分配器粒度和其他开销仍需要额外余量。
>
> 这项工作先解决固定资源下的可运行性。CPU 到 GPU 的传输以及磁盘 I/O 都有代价，目前没有同条件原生 AdamW 吞吐对照，所以不报告加速百分比。

可引用两种独立口径：早期成功 pilot 的 PyTorch allocated 峰值约 69.5 GiB、reserved 约 72.6 GiB；后续完整四轮对照 ACTIVE 整卡采样峰值约 70.52 GiB。不能把不同批次、不同口径的峰值相减作为严格显存降幅。也没有严格 60 GiB 完成训练的验收结果。[资源边界](history/RECOVERY_AND_ACTION_POOLING.md#恢复执行与资源边界)

### 为什么还要落盘直接 offload 到 CPU 不行吗

> CPU 内存也受限。Actor 和 Critic 各有一套 FP32 moments，全部堆到主存会形成新的瓶颈。所以当前活跃角色的 moments 放在 pageable CPU，非活跃角色校验后落盘；角色切换时再受预算约束恢复。代价是切换延迟和磁盘占用，因此这是容量与速度的取舍。

落盘按块写文件，校验长度和 SHA，执行 fsync 并原子更新 manifest，成功后才释放内存。恢复还需核对参数顺序、shape、dtype 和对象身份。[状态存储](../src/agents/optimizer_state_store.py)；[阶段切换](../src/agents/chunked_placement.py)

### 落盘是不是就支持崩溃后断点续训

> 这套 moments 文件是同进程角色切换的 scratch。它依赖原参数、optimizer 和 step 对象继续存在，不包含恢复整个训练所需的所有状态。部分参数更新或 I/O 转移失败后会停止执行，不自动重试半次更新。
>
> 我们另有实验单元粒度的编排恢复：核验已完成 cell 的身份与产物，只继续剩余任务。这个粒度和保存完整模型、optimizer、critic、RNG、采样器位置之后的断点续训不同。

面试官若问完整续训应保存什么：模型、两角色 optimizer/调度器、critic、RNG、数据顺序与位置、policy step、配置及数据身份，并保证状态来自一致的更新边界。列出这些要求不代表项目已经全部实现。

### 共享 GPU 怎么协调是不是独占显存

> 我们做的是本项目内的阶段准入和生命周期协调。worker 进入初始化、rollout、更新等阶段前检查实际容量，让本项目 holder 暂停并释放占用。整个活跃训练臂期间 holder 保持暂停且为空，等专用 systemd cgroup 确认没有存活任务后再恢复。
>
> 身份判断结合 PID、进程启动时间和 cgroup，避免 PID 复用或只看父进程。父进程退出但 GPU 子进程还活着时，不能补回显存。lease 约束本项目进程间协调，释放后到新分配之间仍可能与外部任务竞争。

cgroup 在这里用于任务生命周期识别；它本身不等于 GPU 显存硬配额或驱动级独占锁。[资源协调器](../src/agents/gpu_memory_coordinator.py)

### vLLM sleep 和权重同步分别解决什么

> sleep 主要解决生成和训练阶段的显存复用。权重同步解决下一批 rollout 使用哪一版 policy。仅仅让引擎休眠或成功生成，都不能单独证明它加载了更新后的 actor。框架提供切换和同步，我的资源扩展在这些阶段管理状态和容量。

如果被追问训推一致性，分开检查模型与 tokenizer 身份、模板与真实输入 token、温度等采样参数、policy step/同步路径、teacher-forced log-prob。不同执行路径的数值差异和一次 greedy 输出分叉，不能单独归因于一个框架错误。没有自己核对过的同步 API 不背函数名。

vLLM 官方对休眠能力的解释见 [Sleep Mode](https://docs.vllm.ai/en/latest/features/sleep_mode/)。当前文档帮助理解概念；项目具体行为由固定的 vLLM 0.9.2、verl 0.7.0 和 Agent-R1 提交决定。

### XOR 归档为什么压缩率这么高

> 同一基座经过短程微调后，导出权重的字节可能保留较多共同信息。实现上对名称、shape、dtype 对齐的 tensor 原始字节和共同基座做 XOR，再对差分压缩。恢复时解压并和同一基座再次 XOR，恢复原始字节，然后逐分片核对 hash。
>
> 一次真实 round trip 中，原文件 8,822,893,976 bytes，归档 125,192,339 bytes，约 8.22 GiB 到 119.4 MiB，节省约 98.6%。共享基座仍必须保留，压缩率依赖这次模型与基座的相似性。归档需要先恢复，不能当成 119 MiB 可直接推理的模型。

短程训练、BF16 表示等可能帮助形成可压缩差异，但没有把它们分别消融，不能认定唯一原因。XOR 是可逆变换，体积缩小来自后续压缩；它不是量化，也不省推理时模型显存。[归档代码](../src/agents/parameter_grid_archive.py)；[原始收据](../runs/m2-grid-preparation-20261006/archive-roundtrip-v2/roundtrip_receipt.json)

### OOM 或任务卡住时怎么定位

> 先确认失败发生在哪个阶段，再核对当前进程树、GPU 实际空闲、allocated/reserved 和 cgroup 主存事件。生成阶段检查模型、KV cache、输入长度和并发；更新阶段检查参数、梯度、激活和 moments；主存不足则检查 offload、恢复峰值及文件缓存。资源足够却轨迹不结束时，再检查是否是模型反复拒单。

一个实际问题是 controller 的预检意外创建 CUDA 上下文，改变了对驻留显存的判断。处理方式是隔离需要 CUDA 的预检子进程，让 controller 的 CPU 准备保持不初始化 CUDA，然后核对真实 worker 阶段。只调小 vLLM cache 比例不足以解决 optimizer 更新阶段的峰值。[恢复执行记录](history/RECOVERY_AND_ACTION_POOLING.md#恢复执行与资源边界)

### 如果给多卡或更大的机器你会怎么改

> 当前实测主要是单卡执行。扩展时先量各阶段耗时与峰值，再决定把哪些角色分离。训练侧考虑 FSDP/ZeRO 等分片和并行策略；推理侧看并发、批处理和权重同步成本；采样侧还要处理环境长度差异和慢轨迹。需要重新验证逻辑 batch 的身份、优势归一化范围和预算公平性。

这是一项扩展设计回答，不是已完成多机多卡的成果。更宽裕的内存可能允许去掉磁盘交换、换回更高效的优化器路径，但应以同条件的端到端耗时与有效训练量验证。

## Agent 和后训练高频追问

### 为什么先 SFT 后 RL

> 初始模型在工具语义、仓位和拒单恢复上存在问题。如果先让 RL 处理大量无效循环，很难判断是在优化策略还是学接口。SFT 用环境可重放的示范建立共同起点，再让各 RL 臂独立从同一模型出发比较。

早期共同数据集是 1,212 条；在重复 Train 验收中，非法请求汇总率从 12.44% 降到 1.55%，但收益与成本未全面改善。后续恢复 SFT 另用了 384 条示范、72 次更新，并完成 1,200 条固定验收。这是两个阶段，不能把样本数、错误率或更新次数拼成一次实验。[初始化记录](history/INITIALIZATION_AND_4B_LEARNING.md)；[恢复结果](history/RECOVERY_AND_ACTION_POOLING.md)

### GRPO StepPO GSPO 分别是什么你改了哪里

> GRPO 在这个研究设计中是无 learned critic 的轨迹结果对照，根据同组结果构造相对训练信号。StepPO 是项目沿用的按环境交互步骤组织 critic 和优势计算的训练方案。当前 M1/M2 的实际 actor loss 用 GSPO，额外信用信号加在 GAE 之后。它们分别涉及优势估计、步骤组织与策略 loss，不能只凭都按组采样就当成同一个算法。

M2-plain 仍有 critic、GAE、共同 gate 和同一 GSPO loss，并非标准 GRPO。项目没有完成正式五臂全部性能比较，不能称“已经稳定超过 GRPO”。具体 StepPO/GSPO 实现属于锁定上游，个人贡献应落到接入、扩展和验证。[研究梯度与实现范围](../README.md#research-question-and-implemented-mechanism)

### M1 M2 和 plain 的公式是什么

对轨迹 i 的实际交互步数 T_i，基础奖励保持总量守恒，末步吸收浮点余差：

```text
r_it = Y_i / T_i
```

共同拒单罚实验中，两臂都改成 `r'_it = r_it - 0.05 × invalid_it`；额外 M2 residual 仍使用原金融 `Y`。

```text
delta_t = r'_t + gamma × V_(t+1) - V_t
U_t = delta_t + gamma × lambda × U_(t+1)
critic_return_t = U_t + V_t

M1:       extra S_t = 0
M2-plain: S_t = Y_i - mean(Y of four siblings)
M2-pool:  S_t = mean(Y of siblings with action family a_t) - mean(Y of four siblings)

actor A_t = Whiten_over_real_steps(U_t + eta × S_t)
```

Plain 和 pool 使用相同 gate：至少两个合法推进动作族才启用。`retrieve/compute/invalid` 额外 S 为零；它们仍有基础 GAE。S 不进入 reward，不进入 critic return，也不再经过第二次 GAE。共同拒单罚会同时改变两臂 GAE 和 critic target，不能说 critic 永远没变。

**最容易讲的例子：** 四条终分 `[0,2,4,8]`，动作为 `[buy,buy,hold,sell]`。整体均值 3.5；buy 均值 1。Plain 为 `[-3.5,-1.5,0.5,4.5]`，pool 为 `[-2.5,-2.5,0.5,4.5]`。区别是是否把两条 buy 的差异平均掉。[实现](../src/rewards/sibling_credit.py)

GAE 的一般直觉是综合多步 TD 误差、在偏差和方差间折中；本项目使用步骤级状态值。受测筛选配置中曾使用 gamma=lambda=1，不应机械套用“调 lambda 已经降低方差”的泛化说法。[GAE 原论文](https://arxiv.org/abs/1506.02438)；[本项目实现](../src/agents/screening_runtime.py)

### 奖励 金融评分和 advantage 有什么区别

> 金融评分 Y 是完整轨迹结束后的评价；reward 是交给优势计算的时间序列；advantage 是结合未来 reward、critic 和归一化后进入 actor loss 的学习权重。一个轨迹最终赚钱，不代表每个动作 advantage 都为正；一个非法动作即时 reward 为负，也不保证它最终 advantage 为负。

当前 screening 的金融分数为：

```text
Y = (R_net - B) / max(sigma_benchmark, floor) - risk_lambda × RiskPenalty
```

`R_net` 已含成本，B 为同账本等权基准，分母使用基准波动与 Train 标定 floor；风险项涵盖回撤、超额换手和集中度，按实现取最大值。历史研究稿的 `A_fin` 分母不同，回答当前实验时不要混用。[screening scorer](../src/rewards/screening.py)

### 为什么非法动作会有正 advantage

> GAE 看的是相对当前 value 预测的后续回报，不是合法性的分类标签。共同终分分配、后续行为及 critic 误差都可能让一个非法步骤得到正 advantage。M2 的非法步骤直接 residual 为零，也不等于最终 actor advantage 为零。
>
> 排查时要串起来看实际 reward、critic、GAE、归一化后的 A 和真实 actor loss。还要看更新前后 log-prob：即使 A 为正，共享参数、多样本联合梯度与 KL 等也会影响单个响应，不能仅凭符号断言更新后一定更容易生成。

早期复核中，M1/M2 各有 34/111、38/95 个非法步骤的实际 A 为正，其中更新后平均 log-prob 上升分别只有 17/34、18/38。[信号诊断总结](history/INITIALIZATION_AND_4B_LEARNING.md#两轮八轮与日期覆盖)

### 为什么 pool 没比 plain 好

> 最初希望同一动作类别的多次结果平均能减小随机波动。但同一天不保证相同状态，同为 buy 也可能买不同股票、调到不同目标权重。如果把真实差异一起平均，信号会变平滑却不一定更准确。

存档诊断中，排除初态后 90.8% 的同日兄弟组前置组合不同；可池化组中 60.3% 的同族成员具体订单不同。残差能量下降不能直接解释成已去除噪声。旧 gate 还可能把“全是 buy、具体订单有差异”的组完全置零。这些现象支持拆解比较对象与目标，但尚不足以单独证明最终收益差的因果来源。[机制诊断](history/CREDIT_ORACLE_DIAGNOSTICS.md#存档分析池化生效不等于-credit-更准确)

### 同前缀和 EST REF 具体在做什么

> 先固定完整的模型可见前缀和金融状态，在相同输入下采样候选订单，再让同一策略继续到原终点。EST 是构造 credit 的随机后续，REF 使用独立种子的后续，只用来离线评价。这样可以减少“用同一批随机结果既估计又评分”的问题，并检查是否真的在比较可比动作。

同前缀还要求工具 schema、错误反馈、记忆和真实 token 一致；只匹配持仓向量不够。REF 是有限 Monte Carlo 代理，不是精确 Q。固定后续全部 hold 的 Q 也不同于原策略继续行动的 Q，不能混作同一个目标。

10/19 在同八个 Train 窗口上换独立种子复验，314 条后续完成；112 个共同支持槽中，zero MSE 约 0.140，预设 alpha=.25/.5 的 exact 收缩约 0.085/0.064。预先固定的参考分半方向复现，但尚不能选择最优 alpha、外推跨日期或声称 RL 收益提高。Zero 只指附加 S 为零。[当前结果与边界](CURRENT_STATUS.md)

### 怎么避免未来数据泄漏和挑结果

> 观察读取强制 available_at 不晚于 as_of；特征与标定只用允许的 Train 信息，交易按 next-open 加费用执行。离线教师可以用 Train 内未来结果构造监督标签，但未来结果不能进入模型当时的输入。
>
> 实验预先固定预算、终点、窗口和对照。保留失败、缺失和原分母，不把未完成轨迹补成零收益，不只报最好 checkpoint。反复查看的 Train 开发日期、换 seed 或日期隔离都不自动等于 untouched OOS；当前方法开发未开启正式 Valid/Final OOS。

这些约束降低可检测的泄漏与选择偏差风险；它们不证明预训练参数污染或所有隐性泄漏都已消除。[评估边界](../EVAL_PROTOCOL.md)；[当前状态](CURRENT_STATUS.md)

## 三个可以练熟的难点故事

### AI Infra 主讲优化器状态

> 我遇到的主要约束是单卡和主存都有限，而 RL 同时有多个模型角色。先按初始化、生成、更新阶段测资源，确认只降低生成缓存不能处理更新峰值。方案是让训练参数留 GPU，活跃 optimizer moments 留 CPU，非活跃角色落盘，更新时按块搬运。关键不是把文件写出来，而是保证 step、参数身份、全局裁剪和状态生命周期不被改变。验证分为原生 AdamW 的 CPU 多步数值对照，以及真实 4B 两轮角色更新和恢复。代价是传输和 I/O，没有速度对照前，我把结果表述为容量与正确性上的工程完成。

主讲前必须能答：一块是什么、moment 有几份、step 怎么加、角色切换时保留什么、I/O 中断怎么办。

### Agent 主讲拒单循环

> 模型已经持有超过 20% 仓位，却反复请求买到 20%，每次被拒绝后继续重复，最终耗尽请求预算。输出短而正常结束，所以不是长思考或截断。检查发现拒单上下文保留不足；单独增强反馈仍有失败，于是把错误订单、精确仓位和方向反馈保留下来，再用恢复示范与正常回放共同 SFT。最后 1,200 条固定验收通过，240 条完整回合里的 819 次拒单都在下一请求恢复。这个结果说明受测范围内不再因这些拒单卡死，同时也暴露出模型仍会犯错。

主讲前必须能答：目标仓位与增量买入的区别、拒单是否推进日期、为什么只改提示不够、如何避免训练验收混用。

### 算法主讲负结果改变实验设计

> 原先希望按动作族平均结果降低噪声，完整对照却没看到 pool 稳定优于 plain。进一步检查发现，池化确实压低了 residual 能量，但大部分后期兄弟状态已经不同，同一动作族还混合了不同具体订单。这让我把“信号变小”与“估计变准”分开。随后先做状态回放、gate 单因素验证，再做同前缀采样和独立随机后续，检查具体订单 credit 与收缩。目前有有限参考下的误差方向复现，下一步才是学习验证。

主讲前必须能答：plain 是什么、pool 改了什么、误差相对什么目标、哪些结果是确定性恒等、哪些是随机样本证据。

## 面试前怎么练

第一遍只练三十秒和九十秒介绍，能不用稿讲出“问题、系统、个人模块、结果和下一步”。把每个陌生缩写换成自己能解释的中文。

第二遍只选一个主讲难点，准备一张图、一个函数和一份结果。AI Infra 可选 `chunked_adamw_step`；算法可选 `compute_sibling_credit`。从输入、输出、关键边界和验证说明自己理解了什么，不必背行号。

第三遍模拟连续追问，每题先用两三句话回答，再根据追问展开：

1. 用两分钟介绍项目，明确你个人负责什么。
2. 画出一个 batch 从采样到参数更新的过程。
3. 4B 模型的显存主要花在哪里，为什么搬 moments。
4. 用四条轨迹算出 plain 与 pool 的差别。
5. 方法没有优势，你根据什么决定下一步。
6. 哪项成果有真实 GPU 运行，哪项只是静态检查或机制实验。
7. 说出方案的一项代价，以及你还没验证的一个问题。

遇到不熟悉的上游细节，可以直接说：“这个内核由上游提供，我做的是这层接口和验证；我能说明输入输出以及我观察到的约束，内部实现细节需要再核对。”然后回到自己能举证的部分。

讲述的标准是解释你做了什么判断、为什么这样改、用什么确认结果。先熟练回答这些问题，再扩展模型原理与论文比较。
